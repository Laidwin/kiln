Kiln publishes an API reference under `/api/`, with a link at the bottom of the sidebar. For an HTTP API described with OpenAPI, and for Python, Kiln renders it itself, with the site's theme and search. For other languages, it publishes the HTML your usual tool generates.

## REST APIs (OpenAPI)

Point `docs.yml` to an OpenAPI 3.0 or 3.1 description, in YAML or JSON:

```yaml title="docs.yml"
api:
  openapi: docs/openapi.yaml
  server: https://api.example.com   # optional
```

This site documents a sample API this way, the **Pottery Studio API**: browse [its reference](/api/rest/) to see the result, or read [its description](https://github.com/Laidwin/kiln/blob/main/example/openapi.yaml).

Kiln builds a reference in the manner of hosted API references:

- an **introduction** from `info`: description, base URL, authentication schemes, and every operation grouped by tag;
- **one page per operation**, listed in the sidebar with its HTTP method: the endpoint, the authentication it needs, its path, query and header parameters, its request body and its responses, each field with its type, whether it is required, its allowed values and its description. Nested objects fold open on demand;
- a **right-hand column** with the request in cURL, JavaScript and Python (the language you pick follows you from page to page) and an example response for each status;
- **one page per schema** of `components.schemas`, with an example and the operations that use it.

Examples come from the `example` and `examples` of the description; when there are none, Kiln builds one from the schema (types, formats, enums, defaults). Samples use the first server of the description: `server` gives the host of a relative server URL (`/v1`), or replaces the host of an absolute one. The description itself is published next to the site, for clients and code generators, and linked from the introduction.

Alone, the reference lives under `/api/`. Next to a Python reference (as on this site), the Python one keeps `/api/` and the REST one moves to `/api/rest/`; the sidebar then shows a **Python API** and a **REST API** group.

Tag names become group titles; set `x-displayName` on a tag to choose another title. Descriptions are Markdown. External `$ref` files are not followed: bundle the description into one file first (for example with `redocly bundle`). Kiln checks every local `$ref` at startup and reports the line of a broken one.

:::note
There is no "Try it" button: from a static site, sending requests needs the API to accept cross-origin calls, which most APIs, especially self-hosted ones, do not.
:::

## Python

Kiln never runs Python: that would require every language's SDK in the image. Instead, [griffe](https://mkdocstrings.github.io/griffe/) writes a JSON description of the package, and Kiln turns it into pages. griffe reads the source code without importing it, so the project's dependencies are not needed.

```sh
pipx run griffe dump my_package --search src --docstyle google --full --output api.json
```

Then point `docs.yml` to the file:

```yaml title="docs.yml"
api:
  python: api.json
  exclude: [my_package.tests]   # optional
```

This site documents a small sample package, `pottery`, this way: browse [its reference](/api/) to see the result, or read [its source](https://github.com/Laidwin/kiln/tree/main/example/src/pottery).

Each public module gets a page with its classes, functions and attributes: signatures, then the parameters, return values, exceptions and notes of the docstrings (Google, NumPy or Sphinx style, set by `--docstyle`). Type names link to the classes they refer to, and every page is indexed by the search. Names starting with `_` are left out.

With `kiln serve`, the pages update when `api.json` changes: run the `griffe dump` command again after editing docstrings.

:::tip[In CI]
The GitHub Pages workflow runs griffe for you: set `python-package` (and `python-path` if the package lives in `src/`). See [Publishing](/guides/publishing/).
:::

Add `api.json` to your `.gitignore` if it is generated in CI.

## Other languages

Generate the HTML with your usual tool into an `api/` folder at the project root. Kiln then:

- publishes it untouched under `/api/`;
- adds an **API reference** link at the bottom of the sidebar;
- serves it in `kiln serve` as well, so links can be checked locally.

<Tabs syncKey="lang">
	<TabItem label="Java" icon="seti:java">
		```sh
		mvn javadoc:javadoc
		cp -r target/reports/apidocs api
		```
	</TabItem>
	<TabItem label="C#" icon="seti:c-sharp">
		```sh
		docfx metadata && docfx build -o api
		```
	</TabItem>
</Tabs>

Any static HTML works: rustdoc, TypeDoc, godoc, Doxygen… The only requirement is an `index.html` at the root of `api/`.

:::tip[In CI]
Generate the reference in a job step before the Kiln build, and it will be published with the rest of the site. See [Publishing](/guides/publishing/).
:::

:::note
Pages of an `api/` folder are not indexed by the site search, which keeps results focused on your guides. A project uses `api.openapi`, `api.python` (or both), or an `api/` folder.
:::
